# 草くらべ

GitHubで2026年から活動を始め、毎日コミットを続けたい人が、「毎日続けた場合の草」と自分のGitHub草カレンダーのスクショを上下で比較する、1ページのWebアプリ。
開発を通じて、日付入力からカレンダーのデータと表示を組み立てる仕組みを学ぶ。

> 企画・README案の段階です。アプリの実装、動作確認、利用者による評価、公開は未実施です。以下は予定仕様です。

## 1. サービスとしての目的

- 誰が使うか：GitHubで活動していて、毎日コミットを続けた場合の見た目を知りたい人。
- どんな場面で困っているか：自分の活動の記録は見られるが、一定期間毎日続けた姿を具体的に想像しにくい。
- このアプリでできるようになること：2026年内の指定期間の全日に草が生えた表示を作り、自分の実際のスクショと見比べられる。
- 最初に試してもらう相手：まず制作者本人（2026年にGitHubを始め、2026年の草カレンダーを持つ）。その後、同じようにGitHubで学習を記録している知人1人を想定（未確認）。

## 2. 今回学ぶこと

- 中心となる学習テーマ：日付の範囲を日ごとのデータに変換し、画面へ反映する仕組み。
- このアプリのどこで使うか：「OK」を押したときの日付検証、日付の列挙、曜日・週への位置変換、草の色の更新。
- 完了時に説明・変更できるようになりたいこと：入力から表示までの流れを説明し、「毎日」を「平日だけ」に変えた結果を予測できる。
- 周辺部分に使う慣れた技術：Vite Vanilla構成・HTML/CSS/JS。Renderの Static Siteで公開予定。実装はCSSでの草カレンダー実装（見た目）から着手する。
- 今回は学習対象にしないこと：認証、データベース、GitHub API、画像解析、複雑なフレームワーク構成。

## 3. 操作と処理の流れ

開始日・終了日（`<input type="date">`、`min`/`max`で2026-01-01〜2026-12-31に制限）を入力して「OK」を押す
→ ①未入力→②日付として不正でないか→③2026年の範囲内か→④開始日≦終了日か、の順で検証する
→ 対象日を文字列（YYYY-MM-DD）のままフラットなSetに格納し、適用済み期間を更新する
→ 初期化時に生成済みの366マス（2026年分）をループし、Setに含まれる日付のマスにだけ緑クラスを付ける。

下部で自分の草カレンダーの画像ファイルを選ぶ（`file.type`でPNG/JPEG/WebP・5MB以下を検証）
→ `FileReader.readAsDataURL`でブラウザ内に読み込む
→ 表示する画像を更新する
→ 下部にスクショが表示され、上部のシミュレーションと比較できる（横幅は揃えず、縦横比を維持したまま表示）。

- 学習テーマが関わる部分：日付の検証・列挙・範囲判定・グリッド上の位置変換。
- つまずきそうな点と対処：
  - 日付はDateオブジェクトでなく文字列（YYYY-MM-DD）ベースで扱い、比較は文字列の辞書順比較、加算は数値分解で行う（タイムゾーンのズレを避けるため）。曜日算出のみ`Date.UTC`＋`getUTCDay()`でDateを使う。
  - 列（週）番号は「2026年1月1日を含む週の日曜日」を基準日として1回だけ計算し、対象日との経過日数を7で割った商・余りで週番号・曜日を求める。
  - グリッドはCSS Gridで組み、1行目をラベル専用行にして月初日を含む列にだけ月名を入れる。曜日ラベルは付けない。
  - カレンダーのマスは期間指定に応じて均一に色が変わるだけの表示専用で、セルをクリックしても何も起きない。
  - 初期化時に366マスをDOM生成し、以後は色クラスの切り替えのみで更新する（DOMの作り直しはしない）。
  - 状態（活動日Set・適用済み期間・DOM参照）はモジュールスコープの変数で管理する。
  - 削除ボタン押下時は表示用データと`input.value`の両方をリセットし、同じファイルの再選択に対応する。
  - まだ一度も「OK」を押していない状態での不正入力は、初期状態（当年の灰色カレンダー）と同じ表示にする。

## 4. 最初に作る機能

| 機能 | ユーザーに必要な理由 | 学習テーマとの関係 |
|---|---|---|
| 開始日・終了日とOKボタン（2026年内限定） | 比較したい期間を自分で決める | 入力値と適用済み状態を分ける |
| 2026年の草カレンダー（CSS Grid） | 毎日続けた場合の姿を見る | 日付の列挙、曜日配置、範囲判定 |
| 適用期間と活動日数の表示 | 何をシミュレーションしたか分かる | 両端を含む日数の計算 |
| スクショ1枚の選択・表示・削除 | 実際の記録を下に置いて比較する | 周辺機能：画像の一時表示 |
| 入力・画像エラーの表示 | 失敗を理解してやり直せる | 不正な入力では状態を更新しない |

### 今回作らない機能

- GitHubログイン、APIによる実績取得、GitHubへのコミットや草の変更。
- スクショの解析、日付の自動読取、実績との差分計算、自動位置合わせ。
- コミット回数ごとの濃淡、曜日別の設定、通知、共有URL、画像出力、履歴保存。
- 2026年以外の年の表示・切り替え（年またぎの複数カレンダー表示は不採用）。

## 5. 人に使ってもらう準備

- 保存するデータ：日付と画像はブラウザのメモリ内だけで保持し、画像をサーバーへ送信しない。再読み込みで消える設計。
- ログインの要否：不要。個人別の保存機能がないため。
- データを見られる人・変更できる人：その画面を操作する人。ほかの利用者へ画像を公開する機能は設けない。
- 入力ミスや処理失敗時の表示：未入力・不正な日付・対象年（2026年）外・開始日が終了日より後の場合は、最初に該当した理由を入力欄の近くに表示し、直前の結果を保つ。画像はPNG・JPEG・WebP、5MB以下を暫定仕様とし、形式違い・超過・読み込み失敗時に説明を出す。前の有効な画像は保つ。
- データの削除方法：画像の削除ボタンで表示・参照・input値を解放する。日付を含む全状態は再読み込みで初期化する。
- 公開先・公開範囲：Renderの Static Siteとして公開予定。公開時期・連絡先は未定。
- 費用の上限・不具合の連絡方法：月額0円を仮の上限とし、有料サービスは使わない。試用時は制作者へ直接連絡、一般公開前に連絡先を決める。
